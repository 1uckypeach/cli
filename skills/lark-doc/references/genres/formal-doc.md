# Genre Contract: Formal Document / 内部正式材料 (`workplace.formal_doc`)

## 体裁规则表（硬约束）

| 规则项 | 规则 |
|-|-|
| presentation_mode / 表达模式 | `normal`；准确、克制，以权威、事实、边界、责任和生命周期体现正式，不堆口号、层级或装饰 |
| 内容逻辑 | 先选规则制度、已批准安排、检查整改 / 台账或已核定正式说明之一；各 subtype 只写完成其读者任务所需的对象、依据、要求 / 发现、责任、核验和生命周期 |
| 事实 / 边界 | 正式性来自已确认权威、适用范围和状态；事实、线索、判断、责任认定分开；现行依据核验效力与范围；外发前确认保密、商业秘密、个人信息和发布权限；`checkbox`仅用于明确要求的内部执行实例，批准 / 归档版须固定为文字快照 |
| 错误 | 因“正式”误判公文、把本 leaf 当方案 / 总结 / 简报兜底、伪造批准 / 生效、网络素材冒充本单位事实、检查线索写成责任结论或措施与发现不对应，任一出现即失败 |

## 适用与收口

仅用于发布已授权的非公文组织规则 / 安排，形成可核验的检查、整改、台账和归档记录，或在特定场合表达已核定组织立场。公文制发走 `official-redhead.md`；待批准方案走 `proposal.md`；高层简报走 `memo-brief.md`；周期状态走 `weekly-report.md`；学习总结走 Retrospective / Report。

“制度、通知、方案、计划、总结、简报、讲话稿、正式”均只是召回词，不能覆盖读者任务。本体裁不是不确定请求的 fallback。

## 子类型与结构

| 子类型 | 必要推进 |
|-|-|
| 规则 / 制度 | 目的与权威 → 范围 / 定义 → 规则 → 责任 / 例外 → 执行、维护与复审；易变操作步骤转 SOP |
| 已批准通知 / 安排 | 对象 → 依据 / 范围 → 已确认事项 → 责任 / 时间 → 反馈；未批准不得写成发布稿 |
| 检查、整改 / 台账 | 范围 / 方法 / 证据状态 → 可观察发现 → 影响 → 对应措施 → owner / 期限 → 核验与变更痕迹 |
| 已核定正式说明 / 讲话 / 致辞底稿 | 讲者、场合、听众与时长 → 已核定立场 → 必要事实 / 理由 → 期望理解或行动；不混入制度效力 |

## 证据与高质量写法

- 规则类按需标 owner、版本、批准 / 生效 / 复审状态；政策只写 what / who / when，易变 how 由 procedure / SOP 承载。
- 检查整改区分用户陈述、原始记录、已复核事实和待补证线索；关键日期 / 数量缺佐证时就近标`[证据待补]`及补证动作，归档补正保留原记录。
- 使用主动、具体且术语一致的表达，明确谁在何条件下必须 / 可以做什么；清单严守用户指定数量与字段，不机械补背景。
- 口头稿按“听一遍能懂”改写：术语首次出现即解释，用可口述句法和必要路标维持听觉主线，并按真实时长朗读校验；不能把书面公文直接断句成讲话，也不能为亲和、金句或舞台效果削弱已核边界或补造讲者立场。
- 权威、依据、适用对象或发布权限缺失时保持草案并使用具体占位；外发条件无法确认时 `blocked`。
