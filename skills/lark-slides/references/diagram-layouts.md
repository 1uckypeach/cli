# Diagram 与 smartLayout 选型

本文件解决“什么内容适合使用 `smartLayout`、应该选择哪一种，以及什么时候必须降级为其他结构”。XML 属性和子元素仍以 [slides_xml_schema_definition.xml](slides_xml_schema_definition.xml) 为唯一协议来源；本文件不定义新的布局类型，也不实现运行时路由或几何计算。

## 能力边界

当前只使用以下四种公开 `layoutType`：

- `solid-pyramid`
- `step-pyramid`
- `filled-up-step`
- `linear-up-step`

不要猜测或提前使用尚未进入当前 XSD 的 cycle、venn、quadrant、fishbone 等类型。`smartLayout` 是服务端生成内部几何的声明式容器；模型负责选择语义、控制容器占位和外部图文组合，但不能控制内部形状坐标。

## 先判断关系，再选择布局

| 内容关系 | 首选 | 适合的表达 | 不适合的情况 |
|---|---|---|---|
| 单一顶点下的层级、价值或主题结构 | `solid-pyramid` | 基础到核心、现实到抽象、底座到愿景 | 各项并列、需要双向比较、标题很长 |
| 逐级扩展的能力或成熟度 | `step-pyramid` | 能力进阶、组织成熟度、从门槛到完整能力 | 需要闭环、分支或明确箭头连接 |
| 单向累积、强度或影响逐级上升 | `filled-up-step` | 体验加深、风险升级、投入增长、连续阶段 | 步骤之间存在回退、分支、条件判断 |
| 轻量里程碑或节奏递进 | `linear-up-step` | 时间推进、发布节奏、观看路径、阶段标签 | 需要序号、长描述或强调体量差异 |

选择规则：

1. 先用一句话描述关系，例如“从现实表层逐级进入梦境核心”。如果这句话不能自然包含“逐级、递进、上升、层级”，不要使用当前四种 smartLayout。
2. 流程页只有在核心信息是“单向累积/升级”时才使用 step 类布局。需要箭头、分支、回路或条件的流程仍用 `<shape>` + `<line>`。
3. 时间循环、人物阵营对照、二维矩阵、组织树和并列模块不应为了使用 smartLayout 而改写语义。

## 四种布局的构图规则

### `solid-pyramid`

- 推荐 3-5 个 cell；层数越多，顶层越窄，标题越难读。
- cell 顺序就是渲染顺序。生成后必须根据截图确认内容的上下方向是否符合叙事，不要仅凭数组顺序猜测“第一个一定在顶部”。
- 序号位于金字塔内部，标题显示在图形侧边。标题使用 2-8 个汉字的名词短语。
- 不把解释性长句塞进窄层。需要说明时，在 smartLayout 外部使用一张图片、短注释或独立文本卡。

### `step-pyramid`

- 推荐 3-5 个 cell，适合每层都需要被清楚命名的成熟度结构。
- 相比 `solid-pyramid`，矩形层更适合长度接近的阶段名；仍不要把段落放进 cell。
- 如果重点是“每一步做什么”，而不是“能力逐层变完整”，改用普通流程图。

### `filled-up-step`

- 推荐 3-5 个 cell；6 个以上会明显压缩横向标题空间，除非标题都很短。
- 标题在色块内部、序号靠近底部，适合用高度和色阶表达增强、升级或累积。
- 它可以表达“连续阶段”，但不等于通用流程图：不要用它表达分支、循环、回退或需要连接线说明的因果关系。
- 深色背景优先使用自定义色板，并确保 cell 标题与序号使用高对比文字色。

### `linear-up-step`

- 推荐 3-5 个短标题。该布局不展示 `cell.index`，不要依赖序号传达顺序。
- 视觉重量较轻，适合作为页面中部的节奏线；页面仍应搭配图片、结论卡或外部说明形成完整主视觉。
- 不适合长标题和描述。若每个阶段都需要解释，改用 `filled-up-step` 加外部说明，或改用卡片流程。

## 与图片和文字组合

不要默认让 smartLayout 独占整页。它只负责关系结构，页面还需要承担主题语境和证据：

- 图文页：smartLayout 占宽约 55%-70%，另一侧放一张与关系直接相关的图片和一句结论。
- 层级页：金字塔放左侧或中部，侧边保留足够空间给渲染器生成的标题；图片不要侵入标题区。
- 阶段页：外部说明只解释整体趋势，不重复逐项标题。
- 同一页不要叠加两个 smartLayout。需要两个关系时拆页，或保留一个主关系、另一个改成简短注释。

`cell.description` 是合法协议字段，但不能假定所有 layoutType 都会以同样方式、同样容量显示它。重要信息必须放在 `title` 或 smartLayout 外部；使用 description 后必须以服务端截图为准。

## 降级决策

| 关系 | 当前替代方案 |
|---|---|
| cycle / 时间循环 | 环形节点与箭头，使用 `<shape>` + `<line>`；标签放环外 |
| comparison / 人物阵营 | 对齐的双栏或三栏卡片，保持平行措辞 |
| matrix / 象限 | 2×2 卡片或坐标象限 |
| branching process / 条件流程 | 节点与有方向的连接线 |
| timeline | 时间轴节点；若只是轻量单向里程碑，可选择 `linear-up-step` |
| hierarchy / 组织树 | 分层卡片与连接线；只有单一顶点的抽象层级才用 pyramid |

## 创建前后检查

创建前：

- 关系与 layoutType 匹配，而不是因为“看起来像图”就套用。
- cell 标题短、平行、层级一致。
- smartLayout 容器不越界，并给外部标题、侧边标签和图片留出空间。
- 重要正文没有只放在 `description` 中。

创建后：

- 回读 XML，确认 layoutType、cell 顺序、标题和配色没有被丢弃。
- 每一页都截图检查；静态 lint 只能识别 smartLayout 外框，不能证明内部文字和间距正确。
- 检查标题是否被裁切、与图片相撞、层级方向是否符合叙事、浅色 cell 上是否仍有足够对比。
- 发现内部渲染不适合内容时，优先换 layoutType、缩短标题或扩大容器；不要用额外 shape 覆盖服务端生成的内部图形。
